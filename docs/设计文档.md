## 1. 功能范围

### 1.1 本期做（IM 基本盘）



* **账号**：注册 / 登录，bcrypt 密码，JWT 鉴权，自己设置昵称。

* **好友**：按用户名搜索、发送好友申请、同意 / 拒绝、好友列表、删除好友。

* **单聊**：与好友 1:1 聊天，消息漫游（换设备登录能看到历史）。

* **群聊**：创建群、搜索 / 加入群、群成员列表、群内发言。

* **会话列表**：左侧最近会话（单聊 + 群混合），按最后一条消息时间排序，显示最后一条消息摘要 + 未读红点数字。

* **消息**：文本消息、历史分页漫游、已读回执、未读数、**2 分钟内撤回**。

* **状态**：好友在线 / 离线、群内 "对方正在输入…"、连接断线自动重连。

* **头像**：先给系统默认头像（按 uid 取色 + 首字），图片上传二期。

* **群管理**：群主可**改群名、踢人、转让群主**；群成员分 owner / member 两档（群管理员二期）。被踢者立即从群移除并收到系统通知。

* **站长后台（超级管理员）**：内置站长账号（首个注册者自动成为 admin）。可看全站用户列表、**封禁 / 解封用户**（封禁后强制下线、禁止登录与发言）。

* **找回密码**：绑定邮箱后可走"忘记密码 → 收重置链接 → 设新密码"；站长后台可直接重置任意用户密码兜底。开发期邮件不真发，重置链接打在后端日志。

### 1.2 本期不做（预留接口，二期）



* 图片 / 语音 / 视频消息（协议字段预留 `msg_type`，本期只发 text）

* 消息表情回复、@人、消息转发

* 好友 / 群备注、群公告、群管理员（群主之外的角色）、群禁言

* 消息搜索、多端消息同步已读（先单端为主，多端在线收消息即可）

* 敏感词、举报

## 2. 技术栈



| 层      | 选型                                     | 说明                           |
| ------ | -------------------------------------- | ---------------------------- |
| 前端     | Vue 3 + Vite + TS + Pinia + Vue Router | 前后端完全分离                      |
| UI     | Arco Design Vue                        | 会话列表、消息流、Modal、Badge 直接用     |
| 大列表    | `vue-virtual-scroller`                 | 长消息流虚拟滚动                     |
| 实时     | WebSocket 原生封装                         |                              |
| 后端     | Go 1.22+ / Gin                         |                              |
| WS     | `github.com/gorilla/websocket`         |                              |
| DB     | MySQL 8.0 / GORM                       | utf8mb4                      |
| 缓存（预留） | 本期不用 Redis；在线状态 / 会话列表先走 MySQL + 内存    | 多实例部署时再上 Redis pub/sub，接口已抽象 |
| 鉴权     | JWT HS256，7 天                          |                              |

**单机性能目标**：1 万 + WebSocket 同时在线，单条消息端到端推送 P99 < 100ms，历史翻页 < 20ms。

## 4. 数据库设计（MySQL 8.0，utf8mb4）

### users

`id, username(唯一), password_hash, nickname, avatar_color, email(可空,唯一), email_verified(bool), role(user/admin), banned_until(DATETIME,可空), ban_reason, created_at, updated_at`

> - `role=admin`：站长。首个注册用户自动置为 admin。
> - `banned_until` 非空且晚于当前时间 = 封禁中；登录、WS 握手、发消息一律拒绝，并强制断开该用户现有连接。

### friends（好友关系，双向）

`id, user_id, friend_id, status(0=待申请 1=已通过 2=已拒绝), created_at`

> 加好友即向 
>
> `(toUser)`
>
>  插一条 
>
> `status=0`
>
> ；同意后双方各插 
>
> `status=1`
>
> （或用一条 + 查询时双向匹配，本期用两条简单直接）。

### groups（群）

`id, name, owner_id, created_at`

### group\_members

`id, group_id, user_id, role(owner/member), joined_at`；唯一键 `(group_id,user_id)`

### password_resets（找回密码）

`id, user_id, token(唯一,随机64位hex), expires_at(15分钟), used(bool), created_at`

> 忘记密码时生成一条并邮件发链接 `/reset?token=xxx`；提交新密码时校验 token 未过期未用过，改完即置 `used=true`。

### messages（统一消息表，单聊 / 群聊共用）



| 字段           | 说明                               |
| ------------ | -------------------------------- |
| id           | 自增主键（全局递增，当时间游标用）                |
| conv\_type   | 1 = 单聊 2 = 群聊                    |
| conv\_id     | 单聊 = 规范化 pair key；群聊 = group\_id |
| sender\_id   | 发消息人                             |
| content      | 文本（≤1000 字）                      |
| msg\_type    | text（预留 image）                   |
| is\_recalled | bool，撤回软标记                       |
| created\_at  | DATETIME(3)                      |
| **索引**       | `KEY (conv_type, conv_id, id)`   |

> **单聊 conv_id 怎么算**
>
> ：
>
> `conv_id = min(uidA,uidB)*1e11 + max(uidA,uidB)`
>
> （uid 在千万级以内不会冲突）。这样两人永远落到同一行索引，不用存两条。

### user\_conversations（**会话列表冗余表，性能关键**）



| 字段                      | 说明                              |
| ----------------------- | ------------------------------- |
| user\_id                | 谁的会话列表                          |
| conv\_type / conv\_id   | 哪个会话                            |
| last\_message\_id       | 该会话最后一条消息（冗余，排序列表）              |
| last\_message\_at       | 冗余时间戳                           |
| unread\_count           | 未读数                             |
| last\_read\_message\_id | 已读到哪条（算已读回执）                    |
| 唯一键                     | `(user_id, conv_type, conv_id)` |

> **为什么必须有这张表**
>
> ：会话列表要 "按最后消息时间排序 + 带未读数"，如果每次现算就要扫 messages 表 group by，人一多就崩。每条新消息到达时，由发消息服务
>
> **给该会话每个成员 upsert 一行**
>
> 更新 
>
> `last_message_*`
>
>  和 
>
> `unread_count`
>
> （群 N 行、单聊 2 行）；打开会话时把 
>
> `unread_count`
>
>  清零并写 
>
> `last_read_message_id`
>
> 。会话列表查询直接 
>
> `WHERE user_id=? ORDER BY last_message_at DESC`
>
> 。

## 6. WebSocket 协议

连接：`GET /ws?token=<JWT>`，握手校验。心跳 25s。

### 上行



```
type ClientFrame =
  | { type:"chat"; convType:1|2; convId:number; content:string }
  | { type:"typing"; convType:1|2; convId:number }     // 正在输入
  | { type:"read"; convType:1|2; convId:number; upToId:number }
  | { type:"recall"; messageId:number }
  | { type:"ping" };
```

### 下行



```
type ServerFrame =
  | { type:"message"; id:number; convType:1|2; convId:number;
      from:{id:number;nickname:string}; content:string;
      msgType:"text"; createdAt:string; mine:boolean }
  | { type:"recall"; messageId:number; convType:1|2; convId:number }
  | { type:"read"; convType:1|2; convId:number; userId:number; upToId:number }
  | { type:"typing"; convType:1|2; convId:number; userId:number }
  | { type:"presence"; userId:number; online:boolean }   // 好友上下线
  | { type:"conv_change"; convType:1|2; convId:number }   // 会话列表有更新（未读/最后消息）
  | { type:"pong" } | { type:"error"; reason:string };
```

## 7. 后端核心：发消息链路 + 性能设计

### 7.1 发消息同步链路（`chat` 帧）



1. 鉴权 + 校验：群聊必须是群成员；单聊必须是互为好友。

2. **写 messages 表**（拿自增 id）。

3. **批量 upsert&#x20;**`user_conversations`：单聊更新对方（和自己）那行；群聊更新所有成员那行，对非当前打开者 `unread_count+1`。

4. 组 `message` 帧，按会话成员在线连接 \*\* fan-out 广播 \*\*。

5. 给未读会话的接收方额外推 `conv_change`，让对端刷新会话列表红点。

### 7.2 Hub 性能要点



* **按 conv 分片锁**：内部用 64 个分片（`conv_id % 64`），每个分片一把锁；广播只锁目标分片，避免全局大锁。

* **一个用户多端在线**：`map[userID][]*Client`，收消息往该用户所有连接写；下线按引用计数减，最后一条连接断开才广播离线状态。

* **每连接带缓冲 channel（256）+ 写超时**：慢消费者直接断开踢出，绝不阻塞 hub goroutine。

* **读 pump / 写 pump 分离**：每连接两个 goroutine，读侧只解析帧，写侧独占写 socket。

* **写库与广播解耦**：发消息主 goroutine 只做 "写库 + 组帧"，fan-out 走分片内轻量遍历；不上 Redis 也能撑单机万级。

### 7.3 压缩与传输优化
- **REST 接口**：Gin 挂 `gin-contrib/gzip`，对 `/api` 响应统一 gzip。最大收益在历史消息列表（一次几十上百条文本）和会话列表，文本重复度高，压缩比常能到 1/5。
- **WebSocket**：gorilla `Upgrader.EnableCompression = true`，开启 `permessage-deflate`，连接建立时与浏览器协商压缩。
  - 权衡：聊天单帧通常几百字节，压缩收益有限，但每连接会多维持一份压缩上下文，**万级长连接时内存会涨**。本期开启，后续若连接数压到单机上限，可关掉 WS 压缩只留 REST gzip。
- **前端静态资源**：Vite 用 `vite-plugin-compression` 产出 `.gz` + `.br`，部署侧 Nginx 开 `gzip_static` / `brotli_static`，首屏 JS/CSS 体积砍掉 70%+。
- 消息体本身是 JSON，不另做应用层压缩（HTTP/WS 层已压过，重复压缩纯烧 CPU）。

### 7.4 前端性能



* 消息流用**虚拟滚动**（`vue-virtual-scroller`），只渲染可视区 ± 缓冲 20 条；上拉到顶再拉 `before_id` 更早历史。

* 收到 `message` 先追加本地队列再节流（requestAnimationFrame）刷视图。

* 会话列表切换时不重复拉历史，Pinia 里按 `convId` 缓存已加载消息。

* 重连后：重新发当前会话的 `read` 上报，拉一次 `conversations` 同步红点。

## 8. 安全与边界



* 密码 bcrypt；JWT 密钥走环境变量；消息内容前端插值渲染（不用 v-html），后端限长 1000。

* 撤回校验：只能撤回自己发的、且在 120 秒内。

* 非好友不能单聊，非群成员不能在群里发言。

* **封禁全链路**：登录时查 `banned_until` 命中则拒绝并发原因；JWT 中间件每次请求顺带校验；WS 握手校验；站长执行封禁时通过 Hub 主动断开该用户所有在线连接并推 `{type:"kicked", reason}` 让前端登出。
* 找回密码 token 用 crypto/rand 生成、15 分钟过期、一次性；邮箱不做强制绑定（未绑邮箱的用户走站长兜底重置）。
